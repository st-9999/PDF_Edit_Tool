# テキスト書き換え（本物の書き換え）設計メモ

> ステータス: **T3（不足文字の補完）完了・T4（UI）未着手（2026-09-17）**
> 関連: [`SPEC.md`](./SPEC.md) §6.1、[`TODO.md`](./TODO.md)「テキスト書き換え」

## 1. 目的と定義

PDF しか手元に無い資料で、**一部の数字や文言を変更する**。

- **本物の書き換え**: ページの描画命令（コンテンツストリーム）内の文字列そのものを置き換える。**元の文字は PDF から消える**（選択・コピー・検索・テキスト抽出でも新しい文字だけが得られる）。
- 白塗り＋上書き（見た目上の書き換え）は採用しない。

### 決定事項（2026-09-17）

| 項目                 | 決定                                                                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 方式                 | 本物の書き換え                                                                                                                                          |
| 元フォントに無い文字 | **(A)** その文字だけ同梱フォント（Noto Sans JP Regular、`public/fonts/`）を埋め込んで描く。文字データとしての書き換えは維持し、書体が変わる旨を警告する |
| 画像編集             | 後回し（本件の範囲外）                                                                                                                                  |

### 2.1 埋め込みフォントの収録文字（最重要）

サブセットのため、輪郭データを持つグリフは各フォントで **100〜250 程度**。

- **数字でも欠ける**: A の 1 ページ目は `7` `9` が無い。A の MS ゴシックは数字を 1 つも持たない。B は `0-9` `.` はあるが `,` が無い。
- 漢字はその文書で使われているもの以外ほぼ無い。
- 同じ文書内の**別のフォントリソース**（同一書体の別サブセット）が不足文字を持つことがある（例: A の 3 ページ目のフォントは `0-9` を全て持つ）。
- フォントによっては TrueType の `cmap` 表が残っており、ToUnicode に無いグリフ（全角数字など）を引ける。`cmap` が削られたフォントもある。

→ 「元フォントに無い文字」への対応（決定事項 A）は**例外ではなく日常的に通る経路**として設計する。

### 2.2 試作による実証（サンプル B、使い捨てスクリプト）

1 ページ目の合計欄「81.9」を「123.4」へ、元フォントのまま右揃えで書き換えた。

- pdf.js の抽出: 「123.4」が得られ、「81.9」は**消えた**。右端 x = 265.09 → 265.10（一致）、同じ `TJ` 内の後続セル「35.1」の位置は不変。
- MuPDF でも「123.4」を検索でき、「81.9」は見つからない。
- **文字幅ぴったりのクリップにより、広げた分（先頭の「1」）が表示されなかった** → クリップ矩形を新しい幅に合わせて広げると正しく表示された。

## 3. 設計方針

### 3.1 処理の流れ

1. **解析**: ページの全コンテンツストリームを連結してトークン化し、テキスト関連オペレータ（`BT/ET` `Tf` `Tm` `Td` `TD` `T*` `TL` `Tc` `Tw` `Tz` `Ts` `Tr` `Tj` `TJ` `'` `"`）とグラフィックス状態（`q/Q` `cm`）を解釈する。1 グリフごとに「文字（Unicode）・フォントリソース・文字コード・位置（ページ座標の矩形）・元データ上の位置（オペレータ番号、配列要素、バイト位置）」を得る。
   - 正解データとして **pdf.js `getTextContent` の文字列と位置**と突き合わせてテストする。
2. **対象の特定**: クリック位置のグリフから、同一行・同一フォントサイズの連続範囲（単語／数値のまとまり）を候補として選び、ユーザーが範囲を調整する。
3. **エンコード**: 新しい文言を 1 文字ずつ、下記の優先順で描けるフォントを決める。
   1. 同じフォントリソース（ToUnicode の逆引き。輪郭データの有無を `glyf`/`loca` で確認）
   2. 同じフォントの `cmap` 表
   3. **同一書体の別フォントリソース**（フォント実体の `name` 表のファミリ名と総グリフ数で同一性を判定）。ページのリソースに追加し `Tf` を切り替えて描く
   4. 同梱フォント（決定事項 A）。サブセット埋め込みし、`Tf` 切り替えで描く。書体が変わる旨を警告
4. **書き換え**: 対象範囲のグリフ要素を新しいコード列に置き換え、`TJ` の数値要素で**幅の差を補正**する。
   - 揃え: **右揃え**（右端を固定。数値の既定）／**左揃え**（左端を固定し後続グリフを固定。文字列の既定）／中央。UI で切替可能にする
   - 対象の直前にある**単純な矩形クリップ**が新しい範囲を覆わない場合は矩形を広げる。複雑なクリップは警告して変更しない
   - `Tj`/`'`/`"` は必要に応じて等価な `TJ` に変換してから置き換える
5. **書き戻し**: 変更したストリームを再圧縮してページの `/Contents` に設定する。他ページと共有されているストリーム・リソースは複製してから変更する。

### 3.2 アプリへの組み込み

- 操作ログに `replaceText { pageId, target, newText, align }` を追加（Undo/Redo は既存の再適用方式）。`target` は**元の**コンテンツ上の位置で表し、同じ範囲の再編集は既存操作の更新として扱う。
- プレビュー: 書き換えのあるページだけを 1 ページ PDF として再構築し pdf.js で描画する。
- 保存・抽出・分割: `buildPdf` のページコピー後に適用する（Worker 内）。

### 3.3 対象外・後回し

| ケース                                               | 扱い                               |
| ---------------------------------------------------- | ---------------------------------- |
| スキャン PDF・アウトライン化文字                     | 対応不可（文字データが無い）       |
| ToUnicode も `cmap` も無く文字を特定できないフォント | 書き換え不可として明示             |
| Type3 フォント・縦書き（`Identity-V`）               | 後回し                             |
| Form XObject 内の文字                                | 後回し（サンプルには無い）         |
| 電子署名付き PDF                                     | 書き換えで署名が無効になる旨を表示 |
| 段落の再配置（折り返し）                             | 対象外。同一行内の置換のみ         |

## 5. T1 実装メモ（`src/lib/pdf/content/`）

| モジュール       | 役割                                                                                                                                                                                               |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lexer.ts`       | コンテンツストリームの字句解析。各トークンが元バイト列上の範囲を持つ。インライン画像（`ID`〜`EI`）の生データを読み飛ばす                                                                           |
| `operations.ts`  | トークンを「引数＋演算子」の命令列にする。TJ 配列の各要素も範囲を持つ。閉じ忘れの配列などは例外にせず解釈を続ける                                                                                  |
| `cmap.ts`        | ToUnicode CMap（`bfchar` / `bfrange` の 16 進・配列形式、サロゲートペア、コード空間）と逆引き                                                                                                      |
| `font.ts`        | フォントモデル（コードの区切り、幅、文字、アセント／ディセント、未対応理由）。Type0 は `Identity-H` のみ対応。単純フォントは ToUnicode → エンコーディング（WinAnsi と `Differences` の `uniXXXX`） |
| `text-layout.ts` | テキスト状態・グラフィックス状態を解釈し、グリフごとに文字・原点・送り幅・本体幅・四隅・元データ位置（命令番号・引数番号・TJ 要素番号・バイト位置）を求める                                        |
| `page-text.ts`   | ページの全コンテンツストリームを連結して解析する入口（`extractPageText`）                                                                                                                          |

- **検証**: pdf.js の `getTextContent`（`disableNormalization`）を正解とし、空白を除いた文字列の一致と、各項目の先頭の原点・末尾（進行方向の位置）の一致を確認する（`pdfjs-oracle.test-helper.ts`）。
  - pdf.js の項目幅は最後のグリフの文字間隔 `Tc` を含まないため、末尾は「グリフ本体の幅」（`glyphWidth`）で比べる。送り幅（`advance`）は仕様どおり `Tc`・`Tw` を含む。
  - pdf.js はサイズ違いで基準線がわずかにずれた文字も 1 項目にまとめる（サンプル A の 15・16 ページで 0.96pt）ため、末尾は進行方向の成分だけを比べる。
- **現時点の対象外**: Form XObject 内の文字（`Do` の名前だけ報告）、`Widths` の無い標準 14 フォント（幅不明のため `metrics`）、Identity 以外の CMap（`encoding`）、縦書き（`vertical`）、Type3、`Differences` の `uniXXXX` 以外のグリフ名（文字は null）。

## 6. T2 実装メモ（同一フォントでの置換）

### 6.1 API

- `replacePageText(doc, pageIndex, replacements)`: 置換を適用し、成功時のみページの `/Contents` を新しい 1 つのストリームに差し替える（元のストリームは変更しないため、他ページと共有していても影響しない）。
- `rewritePageContent(page, replacements)`: 文書を変えずに新しいコンテンツのバイト列を返す純関数（プレビューや Worker で使う想定）。
- `TextReplacement = { start, end, text, align }`: `extractPageText` のグリフ index の範囲 [start, end) を `text` に置き換える。`text` が空なら削除。
- 失敗（1 件でもあれば何も変更しない。全件を返す）: `invalid-range` / `overlap` / `spans-operations`（範囲が複数の命令にまたがる） / `unsupported-font` / `missing-glyphs`（元フォントで描けない文字の一覧）。
- 警告: `clip-not-adjusted`（はみ出すがクリップが矩形でないため広げなかった）。

### 6.2 字形の確認（`FontModel.encode`・`truetype.ts`）

- 候補は ToUnicode の逆引き（単純フォントはエンコーディングの逆引きも）。`unicode(code)` が元の文字に戻るコードだけを使う（書き換え後の抽出・検索で新しい文字が得られることを保証）。
- 埋め込み TrueType（FontFile2）があれば、`CIDToGIDMap`（Type0）または cmap（単純フォント: 記号フォントは (3,0)、それ以外はエンコーディングの文字で (3,1)）で GID を求め、`loca` で輪郭データが残っているかを確認する。空白は輪郭が空でもよい。
- フォント実体が無い・TrueType 以外（CFF など）は確かめられないため対応表を信用する。
- 実サンプルでの判定は T0 の Python による独立調査と一致（仕様書 1 ページ目 F1 = `012368`、F2 = `01234568`、数量計算書 = `0-9` と `.`）。

### 6.3 置換と幅の補正

- 範囲の文字列を持つ命令を「グリフ／TJ 数値」の単位列に分解し、範囲を新しいコード列に置き換えて **TJ として書き直す**（`Tj` → `[…] TJ`、`'` → `T* […] TJ`、`"` → `aw Tw ac Tc T* […] TJ`）。範囲外の単位は元のコードのまま。
- 旧幅 = 範囲内グリフの送り（`(w/1000·Tfs + Tc + Tw) · Th`）＋範囲内の TJ 数値。新幅 = 新しいコードの送り。差 `delta` を TJ 数値（`delta·1000 / (Tfs·Th)`）に変換して挿入する。
  - 左揃え: 新しい文字の後ろに `delta` → 左端と後続グリフが不動
  - 右揃え: 新しい文字の前に `delta` → 右端（送り終点）と後続グリフが不動
  - 中央揃え: 前後に `delta/2` ずつ → 中点と後続グリフが不動

### 6.4 クリップの拡張

- 命令ごとに有効なクリップ（`q`/`Q` で入れ子管理、`W`/`W*` とパス終了命令の組）を求め、パス定義時の CTM でクリップ座標系に変換して判定する。
- **新しい文字がクリップからはみ出した側だけを、元の文字より外へ伸びた量だけ広げる**（ベースライン方向のみ。直交方向は変えない）。Print to PDF のクリップは元の文字の送り幅よりわずかに狭い（例: 353.76 に対し文字終端 353.88）ため、「新しい文字全体を覆う」と元のはみ出し分まで広げてしまう。この規則なら元の文字のクリップのされ方を保てる。
- 広げた座標は外側へ丸める（最小側は切り捨て、最大側は切り上げ。小数 5 桁）。
- 軸に平行な矩形（`re`、または `m` + `l`×3〜4 [+ `h`]）のみ書き換える。それ以外は変更せず警告する。

### 6.5 T2 時点の対象外

- 複数の命令にまたがる範囲（例: Excel で 1 文字ずつ別の `BT` に分かれた数字）→ T4 の範囲選択 UI と合わせて検討。
- 元フォントに無い文字（`missing-glyphs`）→ T3（同一フォントの cmap 経由＋ToUnicode 追記、同一書体の別リソース、同梱フォント）。

## 7. T3 実装メモ（元のフォントに無い文字の補完）

### 7.1 補完の順序（`glyph-resolver.ts`）

書体が変わらないものから順に試し、1 文字ずつ決める。

| 順  | `source`            | 条件                                                                                                                               | 文書への追記                                                                                             |
| --- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 1   | `same-font`         | 元フォントの ToUnicode で描ける（T2）                                                                                              | なし                                                                                                     |
| 2   | `same-font-program` | 元フォント（Type0 / Identity）の埋め込み TrueType の cmap に輪郭のある字形があり、その CID が ToUnicode で別の文字に使われていない | ToUnicode と W に 1 文字分の対応を追記                                                                   |
| 3   | `same-typeface`     | 同じ書体の別フォント（文書内の全ページのフォントから、ファミリ名・グリフ総数・unitsPerEm が一致するもの）の ToUnicode で描ける     | ページのフォントリソースに追加（既にあればその名前）。描画時に `Tf` を切り替え、直後に元のフォントへ戻す |
| 4   | `fallback`          | 同梱フォントの cmap に輪郭のある字形がある                                                                                         | 同梱フォントを組み込み、リソースに追加。警告 `fallback-font`                                             |

- `resolve` は文書を変更しない。書き換えが全件成功したときだけ `commit` で追記を反映する（失敗時はフォント辞書・リソース・オブジェクト数とも不変）。
- 同じ文書で複数回書き換えても、同梱フォントは 1 つのフォント辞書にまとめ、字形・ToUnicode・W を作り直して同じ参照に書き込む。
- 1 つの置換の中で補完方法が混ざってもよい（例: 「7鷗9」→ 2・4・3 の順に切り替え）。

### 7.2 同梱フォントの部分埋め込み（`truetype-subset.ts`・`fallback-font.ts`）

- **@pdf-lib/fontkit は採用しなかった**。`embedFont(…, { subset: true })` で Noto Sans JP を埋め込むと、テキスト抽出・幅は正しいのに 7 文字中 5 文字が表示されなかった（部分埋め込みで GID を振り直す処理の不具合と見られる）。`subset: false` なら表示されるが PDF が約 3.2MB 増える。
- 代わりに **GID を保った部分埋め込み**を自前で実装した（Excel 出力と同じ方式）。使う字形（＋ `.notdef`・複合字形の部品を再帰的に）の輪郭データを元のバイト列のまま複写し、他は空にする。`loca` は 32 ビット形式で作り直し、`cmap`・`GSUB` など PDF の CID フォントで使わない表は落とす。表ごとのチェックサムと `checkSumAdjustment` も計算する。
  - 実測: 7 文字で約 140KB（非圧縮）、PDF 全体で約 22KB。MuPDF・pdf.js とも全文字が表示・抽出できた。
- 組み込むフォントは `Type0` / `Identity-H`、`CIDFontType2`、`CIDToGIDMap /Identity`（コード＝GID）、`FontFile2`（`Length1` 付き）、ToUnicode、W。フォント名は `PDFEDT+NotoSansJP`。

### 7.3 同梱フォントの出典とライセンス

- `public/fonts/NotoSansJP-Regular.ttf`: Noto Sans JP Regular（静的 TrueType、17,103 グリフ、5.5MB）。npm パッケージ `@expo-google-fonts/noto-sans-jp@0.4.3` の `400Regular/NotoSansJP_400Regular.ttf` を取り出して配置（依存関係には追加していない）。
- `public/fonts/NotoSansJP-OFL.txt`: 同パッケージの `LICENSE_FONT`（SIL Open Font License 1.1）。フォントの同梱・再配布が可能。

### 7.4 実サンプルでの確認

- 仕様書 1 ページ目: 「4」（MS 明朝の cmap → 2）、「7」「9」「.」（他ページの同じ MS 明朝のサブセット → 3）、「,」「鷗」（同梱フォント → 4）。
- 数量計算書: 「81.9」→「1,234.5」（「,」だけ同梱フォント、右揃え・クリップ拡張）。
- 見た目: 2・3 は元の MS 明朝と見分けがつかない。4 はゴシック体になる（警告どおり）。

### 7.5 T3 時点の対象外

- 同じ書体の別フォントからは ToUnicode で描ける文字だけを使う（その別フォントの cmap 経由の文字は使わない）。
- 同梱フォントは 1 書体（ゴシック体）のみ。明朝体の資料では書体が変わる。
- 複数の命令にまたがる範囲（`spans-operations`）は引き続き未対応（T4 で検討）。
